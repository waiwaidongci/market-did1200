# 农贸市场分时卸货试点复盘

对照同期未试点市场，估算试点对车辆排队等候的影响。

澄河区市场服务中心统筹七家农贸市场，其中三家试行按预约时段卸货。 市场门岗记录车辆入队和开始卸货的时间。市场服务中心按市场和日期汇总，分析员过去在表格里对比试点前后均值。现在先核对同期未试点市场和连续观测覆盖，再将等候时间差分、试点前诊断和缺报清单交给运营负责人复核。

- 只看试点市场前后变化，会把节日备货等同期波动算进试点效果。
- 市场缺报时，表格里的前后均值可能来自不同市场。
- 没有单列试点前两段走势，例会难以判断能否用对照组代表同期变化。

## 业务模块

| 模块 | 用途 |
|---|---|
| 试点总览 | 查阅业务口径、当班流程及最新运行。主管可以核对审计记录。 |
| 门岗明细 | 下载「澄河卸货等候_20261026-1115.csv」并核对字段。分析员可导入 UTF-8 CSV，保留数据指纹和原始行。 |
| 差分测算 | 选择批次和参数并提交后台计算，可从运行列表追踪状态。 |
| 试点结果 | 查看业务指标、证据表和解释，通过来源链接回查数据。 |
| 复核决定 | 查看待处理或已完成记录。复核主管可提交试点复核决定及依据。 |
| 报告交付 | 按批查找结果，核对复核状态并下载相应的 CSV。 |
| 区间周账上下限 | 门岗只报各等待区间车数、周账另记同批车总等待分钟时，测算双重差分可达上下限，含跨系统对账与周账更新后的失效重算。 |

## 演示流程

1. 11 月 16 日 09:00，导出 10 月 26 日至 11 月 15 日的「澄河卸货等候_20261026-1115.csv」。
2. 在「门岗明细」导入 146 条市场日记录，核对试点组标记与有效车辆数。
3. 在「差分测算」设置 11 月 9 日为启动日，分段 7 天，试点前偏离阈值设为 2 分钟。
4. 在「试点结果」核对试点组与对照组各保留 3 家，东埠因缺少 11 月 12 日记录被排除。
5. 复核四格等候均值、−8 分钟的双重差分及 0 分钟的试点前安慰剂差分。
6. 在「复核决定」记录东埠的补报要求，评估试点市场是否分流了对照市场的车辆。
7. 在「报告交付」导出结果、平衡样本清单和解释限制，供下次调度例会审阅。
8. 在「区间周账上下限」用门岗区间车数与周账测算双重差分可达区间；再次导入同名周账新版本，观察旧运行标记失效、重算成功后替换。

## 计算口径

- 每行是一家市场一个自然日的车辆平均等候时间，从入队计至开始卸货。启动日计入试点后。
- 从启动日前切出相邻且等长的前段和后段，两段合并为主估计的试点前。启动日起取同样分段天数作为试点后。
- 只纳入三个窗口逐日都有记录的市场。市场与市场日等权，车辆数用于核对覆盖。
- 双重差分＝试点组（试点后 − 试点前）− 对照组（试点后 − 试点前），负值表示相对缩短。
- 试点前安慰剂差分以第二段起点为假启动日，比较两组从前段到后段的变化。绝对值严格超过阈值时提示复核。
- 这一诊断只覆盖两个试点前窗口。因果解释依赖平行趋势、无提前响应和无跨市场分流。缺报筛选也会影响代表性。

### 区间车数与周账约束下的上下限

「区间周账上下限」模块处理另一套上游口径：门岗逐市场逐日只报各等待区间的车辆数（单车分钟未知），周账按市场和自然周（周一起）另记同一批车的总等待分钟。

- 每个市场日总等待分钟的下界为各区间下界乘车辆数之和，上界同理（末区间含 1440 分钟，其余区间上界不含，整数分钟取上界减一）。
- 周账存在且该市场周观测逐日齐全时，周总分钟必须落在各日上下界之和内；落在区间外即按市场和周列为「对账冲突」并指出冲突的市场与周，该周回退为仅用日界。有周账但门岗缺日的周无法核对，不启用周总额约束。
- 平衡面板与均值批次同口径（三个等长窗口逐日齐全的市场，市场日等权），但纳入市场在窗口外的观测也计入其所在自然周的总额约束；跨试点启动日的自然周整体参与。
- 双重差分对每日总分钟是线性函数、各自然周约束彼此解耦。在每个市场周内按日系数正负把可分配的周总分钟贪心填入区间界，即可同时取到全局上下限，且解为整数分钟。无周账的周只受日界约束，结果区间更宽。
- 下载的 CSV 除指标、四格区间与对账表外，附每个市场日可达的下限端与上限端每日等待总分钟；原均值批次的测算流程保持不变。
- 周账按业务名称版本化：同名再次导入生成新版本，引用旧版本的上下限运行立即标记 `stale` 失效并自动登记重算；只有重算运行成功后，旧结果才置为「已替换失效」并写入替换关系（`superseded_by`）。重算失败不替换旧结果，可手动再次发起重算。

## 本地开发

| 组件 | 实现 |
|---|---|
| 前端 | Nginx 与原生 HTML、CSS、JavaScript。`frontend/src/pages` 放页面，`components/common` 放共用表格、图表及表单。 |
| API | Python 3.11、FastAPI、SQLAlchemy。`backend/src/domain` 放本项目字段、业务计算和演示数据，`routes` 放接口，`models` 放表模型。 |
| 后台 | 独立 Python worker，通过 Redis 唤醒，从数据库租约领取计算，CSV 写入共享卷。 |
| 数据 | MySQL 8 存储批次、运行与审计。`backend/scripts/seed_demo.py` 可安全重复执行。 |

改动前端后执行 `docker compose up -d --build frontend`。改动接口或算法后执行 `docker compose up -d --build backend worker`，再刷新浏览器。如需保留数据，停止时执行 `docker compose down`。使用 `docker compose down -v --remove-orphans` 会清除该项目的数据库、Redis 和报表卷。

`.env.example` 中的 `COMPOSE_PROJECT_NAME`、`FRONTEND_PORT`、`BACKEND_PORT`、`DB_PORT`、`APP_SUBNET` 控制项目隔离。`DB_PASSWORD`、`JWT_SECRET` 和 `SEED_DEMO` 为本机演示默认设置。后端 `constants/enums.py` 与前端 `src/constants/enums.js` 保持角色、运行状态和复核状态一致。项目许可证见 `LICENSE`。
